# Dedicated Omnigent Databricks App

This directory is the deployable source subdirectory for the workshop's second
Databricks App. It is a thin control-plane wrapper around the published
`omnigent[databricks]==0.8.2` wheel; the wheel contains the built React SPA.
The existing Workshop Terminal App is deployed separately and is not changed by
this artifact.

## Runtime and provenance

- Python **3.12.x** (`>=3.12,<3.13`) is required by the uv project; `app.py`
  also rejects runtimes older than 3.12.
- Omnigent release: `v0.8.2`
- Release commit: `72746f177eec0266268ebf8b940cef5bd8087ecf`
- Upstream `main` inspected at:
  `d8c7167b162f681bd8e7aef5274777387d8939cb`
- Published wheel SHA-256:
  `ba6609c8c0f32cf55bcb6f1c9d065591e06d676da21a0f9d6704c930316af532`

`upstream-lock.json` is the machine-readable provenance record.
`pyproject.toml` pins the direct dependency and requires Python
`>=3.12,<3.13`;
`uv.lock` pins the complete resolution generated by uv 0.11.15. Databricks
Apps selects uv mode only when `requirements.txt` is absent and both files are
present. This avoids the platform's Python 3.11 pip mode, which cannot install
Omnigent 0.8.2. No Node build, Git checkout, or host-side build process runs in
the App.

## Required App resources

Each Omnigent App requires resources that are dedicated to that App:

1. A Lakebase project, branch, endpoint, and database. Never share the
   Lakebase project with another Omnigent App because migrations and table
   ownership will collide.
2. A Unity Catalog Volume for agent bundles and control-plane artifacts.

Bind them to the App with these exact resource keys:

- `postgres`: the Lakebase database resource, with
  `CAN_CONNECT_AND_CREATE`.
- `artifact_volume`: the UC Volume resource, with `WRITE_VOLUME`.

The App resource bindings inject `AP_LAKEBASE_ENDPOINT`, the standard
`PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER` values, and
`AP_ARTIFACT_VOLUME_PATH`. Do not replace the `valueFrom` entries in
`app.yaml` with IDs or credentials.

The App service principal also needs `USE_CATALOG` on the Volume's parent
catalog and `USE_SCHEMA` on its parent schema. Keep that principal
least-privileged: Lakebase, the artifact Volume, and control-plane resources
only. Do not grant model serving access or inject model keys, PATs, arbitrary
shell credentials, or cloud credentials.

## First-deploy Lakebase grant

The App service principal does not exist until the App is created. Provision
the dedicated Lakebase and Volume, create/deploy the App once, obtain its
service-principal application ID, and connect to the dedicated PostgreSQL
database as its owner. Grant the role the privileges Alembic and the stores
need:

```sql
GRANT ALL ON SCHEMA public TO "<app-service-principal-application-id>";
GRANT ALL ON ALL TABLES IN SCHEMA public TO "<app-service-principal-application-id>";
GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO "<app-service-principal-application-id>";
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT ALL ON TABLES TO "<app-service-principal-application-id>";
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT ALL ON SEQUENCES TO "<app-service-principal-application-id>";
```

Redeploy after the grant. The first start can fail with
`permission denied for schema public`; this is expected until the grant is
applied. The wrapper runs upstream Alembic migrations on every boot before
constructing the stores.

## Process and security boundary

`app.py` starts one uvicorn process bound to
`0.0.0.0:$DATABRICKS_APP_PORT`. It retains the upstream Lakebase-backed
stores, rotating Lakebase OAuth credential injection, UC Volume artifact
store, HostStore registry/router, default runtime capabilities, migrations,
and full SPA.

This wrapper does not start a local host or runner. HostStore is a durable
control-plane store/router and is required for the intended external-host
topology; constructing it launches no native process. The upstream package
still contains its normal process managers and uses default `RuntimeCaps()`,
so this wrapper does not claim to remove those internals. Workshop policy is
that execution belongs on an attendee-owned external host and the App service
principal receives no model, shell, or arbitrary cloud credentials.

Workshop Terminal implements remote authentication with the attendee OBO token
from each authenticated Databricks Apps request. It atomically mirrors the
bearer into the attendee's 0600 `~/.omnigent/auth_tokens.json` record and starts
`omnigent host --server <OMNIGENT_APP_URL> --non-interactive` in an isolated
process environment with no service-principal fallback. The host rereads the
mirror during authentication: browser-driven token rotation replaces older
snapshots, expiry makes the record unusable until a fresh request arrives, and
revocation causes authentication to fail rather than falling through to App
credentials. No static cross-App bootstrap secret is issued or persisted.

Authentication uses the upstream `header` provider. It trusts
`X-Forwarded-Email` and is safe only behind the Databricks Apps proxy, which
authenticates the request and sanitizes forwarded identity headers. Never
expose the uvicorn port through alternate ingress.

## Health and build identity

Before constructing the upstream app, the wrapper writes a unique harmless probe
file inside `AP_ARTIFACT_VOLUME_PATH`, reads it back, and deletes it. The
operation runs as the App service principal and fails startup when the bound
Volume is not writable, does not return what was written, or does not permit
probe cleanup; the generated name cannot traverse outside the configured Volume
directory.

The probe uses the Files API, not the filesystem. Databricks Apps does not mount
Unity Catalog volumes: binding the resource injects the `/Volumes/...` path, but
nothing answers that path locally, so a POSIX probe fails on a healthy Volume and
crashes the App at startup.

The wrapper then preserves upstream `GET /health`. A bare request has the
deterministic liveness contract:

```json
{"status": "ok"}
```

Treat authenticated HTTP 200 with that body as App health and proof that the
startup Volume invariant completed. Upstream also exposes the
installed package version at `GET /api/version` and in `GET /v1/info`.
`app.yaml` publishes `OMNIGENT_BUILD_VERSION` and `OMNIGENT_BUILD_SHA` for
deployment correlation without replacing or modifying upstream routes.
Remote execution-host connectivity is a separate readiness condition and
must not be inferred from bare `/health`.

## Build, deploy, and source limits

Deploy this repository with `deploy/omnigent-app` as the App source
subdirectory. The source snapshot is intentionally text-only and contains no
vendored wheel or copied SPA. Databricks uses `pyproject.toml` plus `uv.lock`
to provision Python 3.12 and install locked dependencies, then runs
`python app.py`; there is no additional build stage.

Databricks Apps rejects source files over **10 MB**. Keep every file in this
directory below that limit. In particular, do not copy the upstream wheel,
`node_modules`, a Git checkout, or generated web assets into this directory.
The pinned public wheel is downloaded during dependency installation.

## Upgrade and rollback

Version changes are explicit. Update the exact dependency in `pyproject.toml`,
regenerate `uv.lock` with current uv against public PyPI, verify the published
wheel contains the SPA and remains deployable, and update every field in
`upstream-lock.json` together. Never change only the release number or float to
a branch.

The committed lock must contain only public artifact hosts. A developer's uv
configuration can silently embed a private mirror in every registry, sdist, and
wheel URL; those URLs are not reachable from Databricks Apps. Before release,
run the focused contract test and confirm:

```bash
python -m pytest tests/test_omnigent_app_contract.py -q
rg 'pypi-proxy\.dev\.databricks\.com' deploy/omnigent-app/uv.lock
```

The `rg` command must return no matches, and CI enforces that every lock URL
host is `files.pythonhosted.org`. If public resolution is unavailable locally,
do not re-resolve through a private mirror. Apply only the reviewed
host-for-host substitution proven in the live App test, preserving package
paths, versions, and hashes, then run the contract test.

Rollback by restoring the previous `pyproject.toml`, `uv.lock`,
`upstream-lock.json`, and build metadata values, then redeploying the same App
against its dedicated Lakebase and Volume. Omnigent migrations may not be
downgrade-safe, so test rollback against a snapshot/clone of the dedicated
database before relying on it for an event.
